## 1. Target architecture

- **One published package: `@ickb/sdk`, single entry point.** Directories `core/`, `order/`, `dao/`, `shared/` are comprehension boundaries, not packages. `shared/` is the ex-utils subtree (root-exportable helpers, incl. `EntityBase`); domain-directory public symbols are exported from the root barrel. (Reconciled with amendment §7.) No subpath exports (may be added additively later). Rationale: the order script's on-chain weakness (see §5 caveat) removes the generic-adoption thesis; per-entry-point costs, not per-package costs, were the real overhead.
- **Root export surface**: the sole name/kind/owner/status inventory is `scripts/tooling/probes/root-export-floor/manifest.json`; prose carries categories only (SDK boundary, managers, typed errors and results, entities, and the community-bot capability floor). Entries are add/update-only. Renaming or deleting a promised name requires an authority-record amendment cited by the change; a rename updates the entry atomically. Phase 2 settles pending names and owners in that manifest; owner/status may advance toward the Phase-3a floor but cannot regress without the same cited amendment. Phase 3a re-points the inventory at the packed `@ickb/sdk` root and permits no pending or expected-missing entries; the committed api-extractor report independently enforces public shape, not a second inventory (amendments §§14 and 29).
- **Ring surface resolution** (supersedes blueprint A5 `RingAnalysis`): no SDK ring aggregate. The SDK exposes the deposit pool with maturity data; the bot computes the one-window kernel in-app. The earlier "ring aggregate" invariant-export decision is superseded.
- **6 workspaces**: `packages/{sdk,node-utils,testkit}`, `apps/{bot,validation,interface}`. Bot and validation absorb their old packages and scripts layers (lib/cli directory split, depcruise-enforced); sampler dissolves into a testkit bin (CSV + `--fixtures` header dump).
- **Architecture-rule ownership**: dependency-cruiser currently owns the production-to-testkit boundary; the merged SDK adds its no-Node-builtins browser-safety rule in the slice that creates that SDK. The oracle's exact-file ESLint override is an accidental-coupling review guard, not a semantic sandbox: it bans static imports/re-exports, dynamic imports, TypeScript import types, direct standard Node loaders, and triple-slash references with no inline bypass. Deliberate computed access, code generation, or copied implementation logic remains a code-review concern; if semantic isolation becomes necessary, use runtime/build isolation rather than expanding a name blacklist. (The former "internal/ never exported" rule is dropped per amendment §7 — the root barrel + committed api report are the export gate.) Superseded and retired: "sdk consumes only core/dao/order public surface" and the generic-tier purity rule (both die with the package merge). Asymmetric-ratio/fast-check testing stays regardless — its justification is now oracle honesty and C1-class regression, not a foreign-token warranty.
- **Versioning**: single `CHANGELOG.md`, changesets dropped. **Version number and npm-registry handling UNRESOLVED** — all five `@ickb/*` names have live history at `1000.0.82`; publishing `0.x` needs an explicit registry decision (deprecate 1000.x with pointer / accept ordering quirk / new name). Blocks only the publish step, nothing else.
- Tech: React + Vite + Tailwind + CCC connector kept in the interface; react-query, React Compiler/Babel, lazy-load machinery dropped. jscpd remains the deep duplication gate. `Type=notify` systemd-native ops replace the launcher. 100% coverage kept, scoped to `src/**`, with the documented `src/cli/*` exclude (vitest cannot observe spawned children).

## 2. Adjudicated decisions (user-confirmed)

- **A**: one package, single entry, as above.
- **B**: coverage ledger, scenario auto-chooser, and target-outcome _contracts_ killed. Kept: per-run classification, `summary.json`, incident files (with `suggestedNextAction`), and a `--target-outcome` **summary echo** (requested vs observed, no ledger machinery). Supersession chain: addendum listed the ledger as keep; best-shape overturned with consumer evidence; user confirmed after the LLM-operator reframe.
- **C**: ring policy → one-window kernel (~30 lines): don't deposit into an already-thick maturity window; don't consume a thin window's last ready deposit; window W ≈ 22 epochs; gap metric alerts.
- **D**: single CHANGELOG (consequence of A).
- **E**: minimal bot policy (~200 lines): match-value-beats-fee, reserve floor + projected post-tx guard + recovery exception, 21/20 shutdown, fixed iCKB float, ring kernel, greedy withdrawals under consensus caps. Monitoring replaces deleted policy — see the alert table (§6).
- **Validation product**: four legs — preflight (chain identity + invocation/reporting of the **SDK-owned full dependency-identity congruence check per amendment §16**), one-shot smoke, **soak** (long-horizon testnet loop: production-style bot + repeating tester stimulus + journal digest), continuous watch. The separate Phase-2 fixture command proves the SDK pins against testkit-owned bytes and SHA256 preimages; validation owns no second resolver. Testnet operation is **LLM-steered** (LLM reads artifacts between runs, steers via flags, writes the journal, may change code); **mainnet is code-only** — no LLM in any fund-touching loop; the harness never invokes an LLM.
- **SDK consumer boundary**: the supported consumers are the Stack bot, the Stack interface, and NervDAO's existing iCKB feature set: CKB/iCKB conversion, receipts, withdrawal requests, orders, collection, balances, maturity, and related history. NervDAO's standalone Nervos DAO and generic transfer paths remain on CCC. No compatibility layer preserves its old Lumos skeletons, `@ickb/v1-core` API, raw-cell API, or prior package signatures. The public workflow is the manifest-owned `snapshot`/`Snapshot`, scan-free `quoteConversion`, typed conversion planning, `completeTransaction`, sign/send, and `SentTransaction.wait`; exact signatures settle in Phase 2 without adding another public inventory. `Snapshot` exposes immutable aggregates and domain values while retaining scan evidence opaquely for planning and completion. Bare account liquid-cell collections, cursor budgets, anchors, selected inputs, compaction, lock-set attestation mechanics, CCC collection options, change indices, and transaction-shape assertions remain SDK internals. Protocol-domain entities may retain their source cells until B4 makes those fields readonly and frozen; this is not compatibility for NervDAO's old raw-cell API. Supported signer families are implemented by internal adapters; inability to attest a complete lock set surfaces only as typed `account_lock_set`.
- **Production bot supervision**: one bounded bot turn is the systemd main process. The unit uses `Type=notify`, `NotifyAccess=all`, `TimeoutStartSec=120`, `RuntimeMaxSec=20min`, `TimeoutStopSec=90`, `Restart=always`, `RestartSec=60`, and `RestartPreventExitStatus=2`. After config parsing, chain-identity verification, signer construction, account-lock discovery, dependency-identity resolution, and one successful committed account read complete — but before planning, signing, or broadcast — the bot awaits `/usr/bin/systemd-notify --ready` without `--no-block`; notification failure exits 1. Readiness therefore proves the candidate can actually read chain state, so blocking `systemctl start`/`restart` is the deployment readiness proof. `NOTIFY_SOCKET` absence skips notification only for development and migration compatibility. The turn envelope is explicit: startup preflight, bounded scans, and one full confirmation window (10 minutes, ratified) must fit inside `RuntimeMaxSec` with margin, and broadcast is admitted only while a full window remains before the deadline — so `RuntimeMaxSec` termination signals a defect, not a routine bound, and the alert table separates it from exit 2. Journald owns structured stdout/stderr; one content-addressed artifact root remains writable. No launcher child, `launches.ndjson`, readiness parser, internal cadence or retry budget, repeated confirmation wait, random jitter, `STATUS=`, `EXTEND_TIMEOUT_USEC`, or watchdog survives in the final design. No explicit `StartLimit*` tuning is needed because `RestartSec=60` exceeds the default `StartLimitIntervalSec=10s`, so the default burst can never trip; revisit if `RestartSec` ever drops below that window.
- **Shared liquid compaction — single-scan anchor rule**: bot and interface use the same SDK rule. For every deterministic signer lock, one uncached ascending exact-lock indexer scan (`order: "asc"`, exact script search, with data) enumerates the account's committed cells; plain-CKB / native-iCKB / protocol classification is client-side. "Oldest" means first in that server order — never CCC's cached `findCells` iterator and never a client-side re-sort. The cursor is only an exclusive continuation key: the API exposes no snapshot identity for a page or traversal, so the bounded multi-page result is best effort and no planning invariant relies on page coherence. Cursor non-advancement, the SDK's fixed documented page/item ceiling, or abort returns a typed `account_scan_limit` failure rather than partial financial state; the bot emits the corresponding alert and the interface reports that no transaction was built. The **anchor** is the first liquid cell yielded for a lock. Every account action consumes the anchor from **every** deterministic signer lock whose scan yields liquid, even if the action otherwise draws from only one lock; only an account with no liquid anchor under any signer lock may run an action fully funded by its required protocol cells. All liquid candidates yielded by the bounded scans are included by default and deduplicated. The SDK compactor alone trims optional candidates in reverse scan-yield order, and only for a concrete protocol or supported-signer limit recorded beside the implementation; it never guesses a generic quota. Anchors and required action, protocol, and funding inputs always survive; if that required set alone exceeds a limit, planning returns typed `required_set_limit`, the bot alerts, and the interface reports that no transaction was built. Coalesce signer-owned liquid change toward the recommended lock into at most one plain CKB and one native iCKB output; an all-in transfer may emit neither. Under canonical extension, concurrent attempts over the same complete signer-lock set share every extant anchor or a stale input rejects. New pages may include appended cells, already-returned cells may die, and reorgs can invalidate that reasoning; those are accepted best-effort behavior. The named residual is account-wide zero liquidity: independently funded protocol-only actions can share no input and both commit. Reads ignore the transaction pool and use no tip fence.
- **Signer-lock completeness**: the signer adapter must atomically enumerate and attest its complete deterministic CKB lock set. The action freezes that set before scanning and re-reads it immediately before signing; inability to attest completeness or any set change returns typed `account_lock_set`, emits the bot alert or interface failure, and signs nothing. Connectors that cannot meet this contract are unsupported rather than silently reduced to the locks they happened to reveal.
- **No durable pending authority**: neither app persists signed bytes, hashes, outpoints, transaction DAGs, statuses, replacement order, replay state, overlays, or a recovery horizon `K`. Each bot process and interface action builds from committed cells, broadcasts once, waits for one bounded depth-zero window, then ends or returns control; depth-aware `wait({depth})` remains public for external consumers. Every committed-body read bypasses CCC cache, and depth waits additionally recheck canonical inclusion. A later attempt normally conflicts through the shared anchor but may hit the named residuals above. CCC cache and pool state are not input-selection or header-resolution authority: inclusion headers for header-dependent operations (receipt valuation and melt, DAO withdrawals) resolve on the money path through no-cache transaction/header reads bound to the current canonical block hash — CCC's cached header path treats wall-clock age as confirmation and never re-checks canonical membership.
- **Hybrid transaction completion**: Stack owns every selected input, exact script/data identity, deduplication, compaction trim, iCKB quantity, protocol output, and liquid change shape. CCC owns signer preparation and its witness-aware fee fixed point only, called with an explicit fee rate and further input collection disabled. Stack keeps the signed fee ceiling and the no-cache broadcast wrapper. Completion must preserve the ordered Stack-selected input set and the complete ordered output shape, allowing only one declared signer-owned plain CKB output's capacity to change or one canonical plain CKB output to be appended. Exact-zero ordinary change succeeds without that output. Positive ordinary remainder below the actual lock-dependent occupied minimum returns typed `insufficient_capacity` and signs nothing; it is never donated as fee or routed into native-iCKB, receipt, order-master, owned-owner, or other typed outputs. Constructor-owned phase-transition reserves remain byte-identical; currently only `receiptPhase2Capacity` deliberately carries such extra completion capacity. Cache-first CCC collectors and independent fee-input discovery leave the money path.

## 4. July-corpus carry-overs (salvage-verified against current code)

Defects to fix in the rewrite (none covered by C1-C10):

1. **ICKB-001 — unbounded aggregate L1 scans** (`collectPagedScan` had no aggregate budget; financial-state scans materialized complete results over a permissionless pool): **fixed**. `@ickb/utils` owns `PagedScanBudget`, a fixed 6400-item allowance with the pages that covers, shared by every component collector of one read and charged for cached cells as well as RPC page items; exhaustion throws `PagedScanBudgetError`, which the SDK maps to `IckbError` code `account_scan_limit`. Scans fail closed and never return partial financial state.
2. **ICKB-023 — forwarded shutdown orphans detached descendants**: signal-forwarding path in `process.ts` never awaits group cleanup (only the timeout path arms it). Moot since amendment §32: no Stack code spawns child processes anymore.
3. **ICKB-018 — waived by maintainer (2026-08-10)**: no credentialed-path RPC providers in use; pathname in endpoint identity is not a leak here. Revisit only if a path-keyed provider is ever adopted.
4. **ICKB-020 — terminal rejection cleared the whole client cache**, wiping unrelated transactions' marks: resolved by deleting whole-cache clearing and `rebuildReady`; later builds use exact committed reads rather than repairing CCC cache state.
5. **ICKB-008 — `waitTransaction` confirmations>0 reorg race** (status and tip read separately, no inclusion re-check): **fixed** in the exported `waitTransaction`. Once the sampled tip is deep enough, inclusion is re-read without the cache and the wait returns only if the transaction is still committed in the same block and hash.
6. **ICKB-022 remainder — pre-admission ambiguity**: derive and retain the local hash for the current attempt, classify the send result, and observe it for one bounded window. Do not persist or replay signed bytes. A later attempt rebuilds from committed state; duplicate intent remains an accepted best-effort residual. Interface counterpart ICKB-014 is resolved by honest current-session timeout wording plus the session mutex: while an in-session attempt is unresolved, the interface blocks new same-account actions and says so.
7. **ICKB-019 — sampler earliest-block search assumes monotone timestamps** (consensus permits decreases): resolved by labeling binary-searched historical rows approximate; genesis and tip remain exact.

Invariants to preserve in the send-path rewrite: the explicit `DEFAULT_MAX_FEE_RATE` guard is load-bearing (`sendTransactionNoCache` bypasses CCC's ceiling); the locally derived hash is the confirmation identity whatever the node returns (amendment §34). Cache marking and `rebuildReady` are deleted with cache-owned pending behavior.

CCC divergences to add to the documented-reasons list: `TransportFallback` shared-index race under concurrency; `TransportHttp` abort-timer leak on failed-primary; WebSocket default transports keeping finite processes alive — the real reasons behind `fallbacks: []`.

Matcher rules that must survive the rewrite: work budget charged per visited pair _before_ feasibility filtering; marginal partial fee computed on the **prepared** serialized size (one empty witness entry, +8 bytes, per preceding order input).

40. **Ring, selection, and floors as the code has them, minus the search (user-ratified 2026-09-06)**: corrects §2-C, §2-E, and amendment §9, and closes the ring-intervention question in `findings-to-investigate.md`. (a) The ring is a dispersion heuristic: keep pool deposit maturities spread over the 180-epoch cycle so a redemption never waits for one concentrated maturity. Segments are the next power of two above the deposit count, not fixed windows: with N deposits the best spacing is 180/N epochs, so windows must shrink as the pool grows; a doubling splits every segment in two so no deposit changes segment for no reason, and at low counts four segments already ask for the best spacing three deposits can have. Under-coverage is density against the pool average; one protected deposit per segment (the anchor, preferring a non-ready one) is the dispersion invariant. (b) The anchor invariant has one owner, the SDK: `ringSurplusDepositFilter` admits only non-anchor deposits and `ringRequiredLiveDeposit` pins the anchor as a live dependency. The interface redeems from surplus only. The bot's ordinary excess withdrawal does the same; the bot alone, in reserve recovery, may take any ready deposit after surplus fails, because an unmatched user order is worse than a temporarily thin segment. That is the only exception and it stays. (c) Selection is greedy only, walked by maturity, for both consumers: a ready deposit closest to its cycle boundary turns into CKB soonest, which is the wait the user feels. The bounded meet-in-the-middle best-fit and the exact-count selector (`withdrawal_best_fit.ts`, `withdrawal_best_fit_support.ts`, about 520 lines, and the exact-count block of `withdrawal_selection.ts`) are deleted. Accepted: in a pool of mixed sizes the interface fills less of a redemption directly and mints a larger standing order for the remainder, which the bot matches; deposits are capped and ring seeds are uniform, so sizes vary less than the worst case. Amendment §9's "within one deposit of optimal" is withdrawn: it fails when the 30-request cap binds, and a stranded remainder clears when liquidity changes, not by looping; neither loses funds. (d) The floors stay demand-derived, correcting §2-E's fixed iCKB float, and are ratified as the code has them: from the book as read before matching, each direction's floor is the smallest partial-match allowance among the matchable orders in that direction, never below the allowance step, and zero when no order is matchable there; an incomplete match search yields zero floors. So the bot holds no inventory floor on an empty book and a minimum-allowance floor otherwise. Known consequences, to be weighed at coding time: a match that just served a direction's last order can still trigger a refill for that direction, because the floor comes from the pre-match book; and an incomplete search can treat inventory as excess rather than retain it. Residual-book floors would be a behaviour change, not a wording one. Refill, ring seeding, reserve recovery, and excess withdrawal key off those floors as today. GPT-6 Astra reviewed the selection question (child thread `withdrawal-selection-astra-20260906-r1`) and verified that greedy never beats best-fit inside the 30-candidate window and matters beyond it; the maintainer chose greedy for both on simplicity and UX grounds.

41. **The completer decides how many withdrawals (user-ratified 2026-09-06; re-evaluate at coding time)**: extends amendment §40(c). After greedy selection by maturity, the number of withdrawal requests a transaction actually carries is found by trying prefixes of the candidate list from the longest down to zero and accepting the first that completes, with the real completer as the only oracle. Rationale: each request costs a signer-owned marker (about 98 CKB for the bot's lock) plus fee, the DAO caps a transaction at 64 outputs, and only completion knows the resulting capacity, so any count bound computed in policy is a copy that drifts; a binary search is rejected because fundability is not monotone in the count (trimming one withdrawal can introduce a remainder order whose two cells cost more than the saved marker; dust remainders and change minimums add further steps), and a raised reserve was rejected because it fixes only the bot while the interface must degrade to fewer direct withdrawals plus a larger standing order, down to one order, never asking the user to lower an amount one order would satisfy. Shape: one `completeWithdrawalTransaction` in the SDK beside `completeTransaction`, taking a per-prefix builder and an optional acceptance predicate; it completes against the sampled funding cells with a frozen fee rate rather than rescanning per attempt, keeps ring classification frozen against the sampled pool so a prefix of surplus stays surplus with the same anchors pinned, rebuilds the transaction per prefix (never deletes entries, since DAO requests and owner markers depend on output positions), and lets only capacity, representability, output-limit, and policy failures advance the loop while transport, scan, signer, and malformed-transaction errors propagate. The interface builder rebuilds the remainder order per prefix and skips an unrepresentable one; k = 0 is the whole-request order. The bot passes its reserve check as the predicate, evaluated on the accepted prefix with its completed fee; reserve recovery stays two calls, surplus then any ready deposit, and a surplus walk ending at zero does not suppress the second. Consequential deletions: the bot's withdrawal-slot prediction (`MAX_OUTPUTS_BEFORE_CHANGE`, outputs-per-action arithmetic, `outputSlots` plumbing, the `insufficient_output_slots` reason, the 58-output pre-completion rejection, the transcript field), keeping only the match's `maxPartials` as a named match-count bound because the walk cannot shrink a fixed match; the planner's output-limit precheck and the withdrawal-side reserve prediction in the conversion class, with the walk catching output-limit failures from the whole prefix attempt including the builders, which already throw; the interface's own completion step and the `not-enough-ready-deposits` failure variant, since an empty direct selection now means "try the order"; and the second reserve evaluation after a withdrawal prefix has passed, while the post-completion reserve guard stays for every other terminal candidate (direct deposits use fixed fee headroom before completion; zero-prefix transactions can be collection-only). Accepted losses: the bot no longer enforces a conservative 58-output ceiling and may seed or withdraw more when a match nearly fills a transaction; an underfunded wallet on a connector whose preparation does network work (JoyID subkeys fetch a proof and scan COTA cells; Rei calls `ckb_requestAccounts`) may wait through several preparations, and whether a connected Rei wallet re-prompts is unverified and must be checked with the real wallet. Prediction tests become actual-limit fallback tests rather than being deleted. GPT-6 Astra proposed and double-checked this shape (child thread `withdrawal-count-simplest-astra-20260906-r1`, two runs). Fundability of a withdrawal set is a property of every transaction the SDK builds for any signer, so it is the SDK's bug to fix once; a consumer-side workaround such as a raised bot reserve is not acceptable. The maintainer requires every part of this amendment to be re-evaluated against the code when it is implemented.
