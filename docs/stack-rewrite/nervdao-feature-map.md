## Product Conclusion

Full NervDAO parity is not the target. The interface should preserve useful user outcomes around funds: what the wallet owns, what the next transaction can collect, what remains unavailable, and which action changes that state. It should not copy screens or metrics whose maintenance cost exceeds their decision value.

### Selected Phase-5 Scope

1. **Resolved balance semantics.** Show wallet-held value, collectable-now protocol value, unavailable value, and observed total for resolved state without mapping NervDAO's pending label onto Stack's different pending bucket. When an order group cannot be resolved, show a warning instead of claiming a complete total or inventing a value for it.
2. **Live position visibility.** List resolved orders, receipts, and withdrawals with value, state, and maturity where applicable. Link currently collectable positions to the existing conversion or collection flow. Keep matchable orders and immature withdrawals visible but non-actionable in this slice.
3. **Planner-derived iCKB Max.** Use native and atomically collectable iCKB from the conversion context without double counting. Treat every matchable order as unavailable so Max never depends on melting a standing order.

### Deferred

4. **Fee-safe CKB Max.** `ckbAvailable` does not reserve output capacity or the later completion fee. Select CKB Max only after a completion-aware owner can prove the displayed amount remains fundable.
5. **Explicit order action.** Preserve pending orders by default. Any later cancellation or replacement action must retain the deployed resolver's best-effort confusion-attack boundary, skip ambiguous groups, and never present an order melt as proof that an old key can be retired.
6. **Position dates and chain-derived iCKB protocol history.** Dates require inclusion-header acquisition that current position models do not own. If history is later selected, a bounded classifier should model one committed transaction with zero or more protocol effects rather than duplicate mixed conversions as unrelated rows. NervDAO's four visible categories, pagination, timestamp, amount, unit, and explorer link are evidence, not a required API shape (`src/cores/queries.ts:473-580`; `IckbHistoryOrders.tsx:21-118`; `IckbHistoryOrderItems.tsx:18-63`).

### Do Not Copy By Default

- **Global iCKB liquidity and seven-day APY.** Total live iCKB needs a chain-wide data owner, and the aggregate does not determine whether this user's conversion can execute. Prefer path, fee, collectability, and maturity information at the action point. The existing rate chart already carries the educational trend.
- **Automatic pending-order cancellation.** It can destroy an intentional standing order and should remain an explicit user decision.
- **Legacy component and query shapes.** They are migration evidence only.

## History Boundary

If selected, history means committed, chain-derived iCKB protocol activity for the connected account. It does not mean current live cells, the current-session pending transaction hash, generic wallet history, failed broadcasts, or generic Nervos DAO activity unrelated to iCKB.

The owner should define stable chronological pagination and zero-to-many effects instead of copying NervDAO's repeated whole-history scans, timestamp-only deduplication, or interleaving behavior. A transaction hash identifies one transaction; its effect list explains the protocol legs within it.
