# Lint Policy Map

This map is the migration ledger for moving lint policy from custom code to existing tools when the tool cleanly owns the invariant. Keep it current with every lint-policy change. If a rule moves, changes semantics, is dropped, or remains custom for a sharper reason, update this file in the same change.

Migration states:

- `keep custom`: keep the rule in repo-owned code because the invariant is repo-specific or the replacement is weaker.
- `replace`: an off-the-shelf tool can own the rule after a proof run.
- `partial`: an off-the-shelf tool can own part of the rule, but a custom remainder or semantic gap stays.
- `defer`: candidate exists, but no migration should happen until a comparison script proves value.
- `planned`: the policy is documented but not currently enforced.
- `drop`: remove the rule because another current rule already fully covers it.

## First Migration Slices

1. Keep direct Vitest modifier syntax in `@vitest/eslint-plugin`. Remove custom `testRunModifier` only if a later ESLint rule or plugin also catches inline reserved option modifiers, expected-failure `fails`, committed retries, option spreads/non-literal computed keys, and the factored-option shape owned by the custom syntax policy.
2. Evaluate `@arethetypeswrong/cli` for publishable packages after deciding whether it should consume pnpm-packed tarballs or package directories.
3. Keep the focused structure linter as the owner for full CKB script equality, paged cell scans, source/test classification and build boundaries, package-local workspace dependency declarations, workflow action pins, public API documentation traversal, and anti-compliance test heuristics.
