## Findings

### High: exhaustive matching rewrite has an unbounded Cartesian cost

`packages/order/src/matching/order_match_search.ts:25` materializes every UDT-to-CKB sequential match, then line 38 crosses that array with every CKB-to-UDT sequential match. `maxPartials` limits selected orders but does not bound subdivisions within one order.

For directional maxima `M1` and `M2` with steps `S1` and `S2`, candidate work is approximately `(ceil(M1 / S1) + 1) * (ceil(M2 / S2) + 1)`. Otherwise identical fixtures with 100, 200, and 400 steps visited 10,201, 40,401, and 160,801 candidates. A standard UDT-order reproduction with a small legal public step reached about 3.3 GB of heap and terminated with V8 out-of-memory.

Impact: the synchronous `bestMatch` call can stall or terminate bot, validation, and external matcher processes. Replace the full cross-product with a bounded exact search using proven upper bounds or Pareto states. If completeness cannot be guaranteed under a bound, require an explicit candidate budget and return a distinct incomplete-search result. Static lint cannot prove complexity bounds; candidate-budget and large-range runtime tests must own this contract.

### Medium: exhaustive rewrite still skips profitable below-step extensions

`packages/order/src/matching/order_match_search.ts:70` considers a residual CKB-budget extension only when the UDT-to-CKB side has no partials. Line 77 applies the symmetric restriction. A residual below the normal step can fund another order after an existing same-direction partial.

With four valid groups, allowance `(11,82)`, exchange weights `(2,5)`, CKB step `29`, UDT step `12`, and cap `3`, current search selected one order with deltas `(-3,+3)` and gain `9`. Extending that match with residual CKB budget `8` selected two orders with deltas `(-11,+7)` and gain `13`; `addMatch` accepted the transaction.

Consider below-step extensions for every under-cap pair and include those cases in the exhaustive oracle. Integrate this with the bounded-search design so completeness work does not worsen the Cartesian cost. This is not statically lintable.

### Medium: corrected order fee still omits prepared witness growth

`packages/order/src/matching/order_match_context.ts:13` now accounts for 112 bytes of input/output serialization overhead, fixing cycle 1's 76-byte undercount for raw order partials. It still omits witness-vector growth in the documented SDK completion path.

When `sdk.completeTransaction` later adds a signer input, CCC places its witness after order inputs and inserts one empty witness entry per preceding partial. That adds eight serialized bytes per partial. A 163-byte order adds 275 raw bytes but 283 prepared bytes. A reproduced candidate had gross gain `279`, modeled fee `275`, and reported net `+4`; prepared marginal fee was `283`, making net value `-4`.

Include the per-partial empty-witness cost for the supported completion path and test size deltas after signer preparation. Match-only bot transactions have a later final profitability gate, but combined rebalance transactions retain this negative marginal match. Serialization contract tests, not ESLint, own the invariant.

### Medium: DAO fee fallback masks its authoritative failure

`packages/sdk/src/client/sdk_base.ts:77` starts the new output-target fallback after ordinary fee completion crosses the DAO output limit. Lines 82-85 catch every fallback error and rethrow the superseded first-pass `DaoOutputLimitError`.

Trigger: a valid target exists, but rebuilding or `completeFeeChangeToOutput` fails because of a transient RPC error, state race, or actual fee-capacity failure. The caller receives a deterministic DAO-limit error without the fallback cause. Bot retry classification then treats the failure as non-retryable. The test at `packages/sdk/test/transaction/complete/complete_transaction_fee_change_fallback_rebuild.ts:122` currently locks in this masking behavior with `target completion failed`.

Preserve the first DAO error only when no fallback target exists. Once fallback execution begins, propagate its failure, optionally retaining the DAO error as secondary context. Error identity/cause and retry-classification tests must own this behavior.
