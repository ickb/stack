## High Findings

### 1. Distinct RPC configurations still collapse to one live-bot identity

The new runtime identity binds launcher run ID, chain, primary lock, bounds, retry policy, and sleep interval, but `apps/bot/src/index.ts:116-129` represents the RPC endpoint only as `rpcConfigured: boolean`. `packages/validation/src/supervisor/stimulus/preflight/liveBotStimulusPrepare.ts:160-216` compares that same coarse field. Two same-chain/account/bounds configurations using different configured endpoints therefore compare equal, allowing validation to certify the requested config while the live bot uses another, potentially stale backend. Add an explicit non-secret endpoint identity or equivalent local non-logging proof. Do not log or hash credential-bearing URL text.

### 2. Active-log growth eventually disables runtime identity proof

`packages/validation/src/supervisor/stimulus/preflight/liveBotStimulusPrepare.ts:97-106` reads the complete active bot event file into memory and only then rejects it above 16 MiB. The active slot is append-only for the child lifetime and is excluded from quota pruning, so a healthy long-running bot eventually makes every later stimulus session fail until launcher restart/slot rotation. The read also allocates before enforcing the nominal bound. This is a new validation impact of cycle 8's unbounded active-log finding. Store canonical startup identity in one dedicated bounded record or read a bounded startup prefix/range; rotate active output by bytes.

### 3. Completed bounded testers remain alive until wrapper timeout

Natural return fixed cycle 10's stdout truncation, but `apps/validation/src/tester.ts:55-56` only sets `process.exitCode`; the default public CCC client created at `:76-78` retains a WebSocket transport and is never closed. Two fresh one-iteration actors emitted complete transaction evidence, then remained alive until their 15- and 30-minute wrapper deadlines and were classified `command_timeout`. Explicitly close/unref the client transport after the tester loop, or use a drain-aware shutdown boundary that preserves stdout. Add a real default-client process test that completes one iteration and exits promptly.

## Medium Findings

### 4. Missing pass-two provenance is misreported as an unrelated hash

The owned transaction hash now reaches the guard, but `packages/validation/src/tester/runtime/freshMatchableOrderSkip.ts:62-76` returns the first unrelated fresh mint when the expected origin is absent. The supervisor then classifies the different hash as malformed provenance. With `ownedTxHash` present, return a distinct expected-origin-absent outcome while still blocking stimulus for unrelated fresh orders. Test expected hash absent with unrelated orders in both scan orders through the production loop/attempt boundary.

### 5. Event retention is count-bounded but not byte-bounded

The scanner now rejects non-bot/malformed lines, caps partial text at 64 KiB, and caps unmatched maps at 256 entries. However, `packages/validation/src/supervisor/stimulus/selection/liveBotStimulusEventScan.ts:321-344` retains arbitrary nested `actions`, while `:576-586` limits only entry count and each read may contain a complete record near the 16 MiB delta limit. The theoretical retained bound approaches the Node heap range despite local-bot trust. Apply per-line and aggregate retained-byte limits and retain only fields required for correlation. Test built-first and commit-first saturation with large complete records.

### 6. Exceptional wait summaries still omit cursor and partial scan state

Slotted paths and completed launcher/choice/stimulus phases are now preserved. `packages/validation/src/supervisor/stimulus/runtime/liveBotStimulusSession.ts:45-103`, however, adds evidence only after a phase returns; the cursor created at `:64-67` is never recorded, and partial scan state is available only after wait completion. A launcher/read failure during waiting therefore loses the baseline and observations needed to reconstruct the boundary. Record the cursor immediately and expose bounded scan progress incrementally. Transaction hashes are preserved on ordinary supervisor timeout; the remaining issue is diagnostic state, not hash loss.

## Low Finding

### 7. Explicit wait deadlines cannot preempt launcher or filesystem operations

`packages/validation/src/supervisor/stimulus/runtime/liveBotStimulusWait.ts:38-82` now caps sleep to the remaining budget and rejects evidence observed after expiry. Launcher proof and `stat`/`open`/`read`/`close` calls remain unbounded awaits, including the final quiescence proof at `:114`. A stalled operation can therefore exceed `--wait-seconds` indefinitely. Apply the remaining budget to each async polling operation and validate timer-compatible argument bounds.
