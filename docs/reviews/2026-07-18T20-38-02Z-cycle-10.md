## High Findings

### 1. Live bot identity is not bound to the preflighted bot configuration

`packages/validation/src/supervisor/stimulus/preflight/liveBotStimulusPrepare.ts:23-58` separately proves a live launcher process and runs preflight against the supplied bot config. `liveBotStimulusPreflight.ts:77-146` binds only process identity and an optional event path; nothing compares the live child's chain, account, config, or runtime bounds with the preflight report. A same-chain bot started from another account/config can match the public tester order and produce a correlated pass, falsely validating the requested bot configuration. Emit one non-secret runtime identity from the current child, bind it to both preflight reports before stimulus, and constrain event correlation to that run and chain. Test wrong-chain, wrong-account, wrong-config, and wrong-run live children.

### 2. Multiple tester hashes can turn an unrelated bot match into a pass

`packages/validation/src/supervisor/stimulus/runtime/liveBotStimulusTesterRun.ts:83-124` requires one created non-dust order but does not require exactly one transaction hash. `selection/liveBotStimulusEventScan.ts:503-524` accepts every valid hash in the created-order evidence, and `:263-281` correlates a match with any one of them. A drifted or malformed one-order summary containing the real hash plus an unrelated valid hash lets the unrelated match satisfy validation. Parse one canonical hash as part of `testerStimulusSucceeded`, reject every other cardinality, and pass that scalar identity to the scanner. Test zero, duplicate, multiple, malformed-plus-valid, and case-normalization shapes.

## Medium Findings

### 3. Pass-two transaction provenance is parsed and discarded

The supervisor passes `--owned-tx-hash`, but `apps/validation/src/tester.ts:60-102` validates and discards it before `runTesterLoop`. `packages/validation/src/tester/runtime/freshMatchableOrderSkip.ts:26-65` then returns the first fresh actionable owned mint, regardless of provenance. If another fresh order appears first, pass two reports the wrong hash and the supervisor raises a false malformed-provenance incident. The process fixture at `apps/validation/test/fixtures/twoPassTesterProcess.ts:11-43` reads `process.argv` itself and manufactures matching evidence, so it does not test production wiring. Pass the parsed hash through loop/attempt state, restrict the pass-two guard to that origin, and replace the self-fulfilling fixture with a real ordering counterexample.

### 4. Pending capital is omitted from tester totals and low-capital decisions

`packages/validation/src/tester/runtime/runtime.ts:69-92` receives the full SDK projection but retains only available CKB/iCKB. `testerAttempt.ts:48-50` computes total equivalent capital from those liquid values, while `:92-117` labels available as total and hard-codes unavailable amounts to zero. `planning/testerAttemptPlanning.ts:214-240` can therefore stop permanently for low capital while a valuable pending withdrawal or order exists. Preserve projection pending and total balances in `TesterState`; use available values for planning and total values for stop decisions/evidence. Test no liquidity plus sufficient pending value.

### 5. The indefinite event scanner is neither fully fail-closed nor memory-bounded

`packages/validation/src/supervisor/stimulus/selection/liveBotStimulusEventScan.ts:62-99` silently discards complete JSON values that are not bot records instead of counting malformed dedicated-sink evidence. The same scanner retains `pendingText`, matched builds, commits, and post-match commits for the whole default no-deadline wait (`:45-58`, `:136-175`); `runtime/liveBotStimulusWait.ts:29-80` bounds only one read delta. Corrupt input can disappear silently, while unrelated commits or repeated partial chunks grow memory indefinitely. Treat every nonblank complete line in the dedicated sink as accepted or malformed, cap pending bytes and unmatched iteration state, and prune paired/obsolete entries without losing reverse-order correlation.

### 6. Direct SDK CKB conversions still reserve raw-order overhead

`packages/validation/src/tester/planning/testerOrderPlanning.ts:153-164` computes SDK conversion fundability through the raw-order budget, subtracting both the CKB reserve and a separate 1,000 CKB order overhead. A direct SDK deposit that preserves reserve and fee headroom but not the unrelated order overhead is rejected. The test named “does not reserve raw-order overhead” at `packages/validation/test/tester/planning/testerPlanningCore.ts:244-268` supplies the entire overhead and cannot expose the defect. Give SDK conversion its reserve-only budget and let completed-transaction reserve enforcement own exact fee safety.

### 7. Immediate CLI exit can truncate supervisor evidence

`apps/validation/src/tester.ts:46-57` calls `process.exit` through `:131-133` immediately after the loop. Structured stdout can still be buffered when the tester is a piped supervisor child, truncating the final NDJSON record into malformed evidence. The bot entrypoint has the same pattern. Set `process.exitCode` and return naturally, as the supervisor/stimulus entrypoints do, and test a real child writing more than pipe-buffer capacity before exit.

### 8. Exceptional stimulus artifacts point at stale paths and lose phase evidence

`packages/validation/src/supervisor/stimulus/runtime/liveBotStimulusSession.ts:43-49` writes `launch.json` before `preflight/liveBotStimulusPrepare.ts:23-31` discovers the launcher's active slotted event path. The catch at `liveBotStimulusSession.ts:84-96` writes through the original paths with only status and failure, dropping the chosen stimulus, tester transaction, cursor, scan state, and authoritative event path. Make active paths and phase evidence session-owned before launch artifacts are finalized, and preserve accumulated public evidence in exceptional summaries. Test failure after tester broadcast on a slotted event file.

## Low Finding

### 9. `--wait-seconds` is not a wall-clock deadline

`packages/validation/src/supervisor/stimulus/runtime/liveBotStimulusWait.ts:29-78` checks the deadline, then sleeps for the full poll interval; launcher proof and filesystem operations are also outside the remaining budget. `--wait-seconds 1 --poll-seconds 5` therefore takes at least five seconds, and a blocked proof/read can extend it further. Sleep only to the remaining deadline, validate timer-compatible bounds, and apply the remaining budget to each polling operation.
