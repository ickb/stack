## Current Findings

### High: real launcher evidence can never satisfy update readiness

`scripts/bot/launcher/index.ts:15` derives the release root with `fileURLToPath(new URL("../../..", import.meta.url))`. For the directory URL used by a deployed launcher, Node returns the release path with a trailing separator. `scripts/ickb-bot-systemd-update.sh:336-339` compares that value by strict string equality with a `realpath`-derived release path that has no trailing separator.

A focused representative reproduction produced `"/opt/ickb-stack-mainnet/releases/release/"` from the launcher expression. The current updater tests hand-author `repoRoot` from the expected release string at `scripts/test/bot/systemd-update.ts:286-326`, so all readiness tests pass without composing the real producer and consumer. A healthy candidate therefore times out and enters rollback; rollback uses the same false comparison and can also be reported unready.

Canonicalize the release path at one boundary and add an integration regression that uses launcher-produced `launcher.started` evidence with the real readiness probe. Mocked equality is not proof of this contract.

### High: the migration path cannot migrate the shipped legacy deployment

The tracked legacy installer generated `ExecStart=/usr/bin/node scripts/ickb-bot-launcher.mjs ...`, used the bare deployment root as `WorkingDirectory`, and left a root-owned `log/bot` containing a service-owned network subdirectory. `legacy_unit_is_compatible` at `scripts/ickb-bot-systemd-install.sh:304-325` instead requires a hybrid shape: the bare deployment root plus `scripts/bot/launcher.ts --no-child-tee`, without the new unit's `--log-root` argument. Neither the shipped legacy installer nor the current installer generates that shape, so an active legacy deployment is rejected before migration. If the service is inactive, the compatibility check is skipped, but `prepare_checkout_copy` resets a copy to the same legacy `HEAD` while `install_unit` switches it to the TypeScript entrypoint that revision does not contain. The migrated launcher must also create metadata directly under the root-owned legacy `log/bot` directory.

Failures after the rename boundary are not recovered: once `scripts/ickb-bot-systemd-install.sh:413-443` stops the service and replaces the layout, `freeze_release`, ownership, unit installation, or `daemon-reload` failure exits under `set -e` without restoring the old unit/layout and service. Current tests assert source structure, not a fixture generated by the shipped installer or post-stop failure injection.

Build the candidate from an explicit migration-capable revision, recognize the exact shipped unit, normalize shared-log ownership without deleting evidence, and retain a runnable legacy rollback command. Cover every operation after stop with one restoration path and prove it using a generated legacy fixture.

### High: failed rollback can delete a release that may still be running

When candidate readiness fails, `scripts/ickb-bot-systemd-update.sh:491-500` ignores a failed `systemctl stop`, switches `current` backward, and attempts restart/readiness. If rollback readiness then fails, `main` removes the candidate whenever the symlink points to the previous target at `scripts/ickb-bot-systemd-update.sh:618-621`.

The candidate process can still be executing from the release being recursively deleted. Even after process exit, this destroys the failed rollout's release tree before rollback readiness is proved. Require confirmed candidate termination before switching away, return an explicit rollback-ready/candidate-removable state, and never use symlink state alone as proof that deletion is safe.

### High: the storage quota does not own all bytes it claims to bound

The child publishes artifacts directly at `packages/bot/src/observability/artifacts.ts:126-159`; the launcher only discovers their size during a later serialized log write at `scripts/bot/launcher/storage/quota.ts:60-79`. An artifact can therefore exceed the remaining quota before admission and race quota scans. A focused 5,000-byte-quota counterexample wrote a 10,000-byte artifact, exited with status 1, left 11,150 bytes, and retained only `launcher.started` because terminal evidence no longer fit.

The inventory at `scripts/bot/launcher/storage/retention.ts:9-28,74-103` also excludes persisted legacy `bot.events.ndjson` and `bot.stderr.log` files that the incident collector still consumes, plus crash-left `.rotate` siblings created by `scripts/bot/launcher/logs.ts`. Counterexamples left 14,251 bytes after two legacy files and 9,000 bytes after one stale rotation file under the same 5,000-byte quota.

Make artifact publication part of the serialized quota owner, reserve terminal evidence before making an artifact visible, inventory every launcher-owned file, and define an explicit preservation/migration policy for legacy evidence. A numeric quota passed to another process is not cross-process admission control.

### High: rotation destroys evidence required by live and incident consumers

`scripts/bot/launcher/storage/quota.ts:191-204` compacts active events to the preflight identity plus the latest record and stderr to one complete line plus an incomplete suffix. Live validation correlates `bot.transaction.built` with `bot.transaction.committed` in `packages/validation/src/supervisor/stimulus/selection/liveBotStimulusEventScan.ts:158-180`, while incident collection relies on timestamped continuation lines. Under quota pressure, a successful run retained preflight and commit but discarded the required build record; consumers cannot distinguish compaction from evidence that never occurred.

Irreducible quota failure also returns status 1 through the launcher while generated units restart every failure except status 2. Persistent quota pressure therefore produces a restart loop that repeatedly reuses slots and further erodes evidence.

Define and reserve bounded semantic evidence units: at minimum the active iteration/transaction correlation sequence, referenced artifacts, terminal launch evidence, and one complete diagnostic block. This requires the single byte owner from the preceding finding; compaction cannot be corrected independently while artifacts and stale files bypass accounting. If that set cannot fit, stop with the restart-prevented safety status after durably recording the reason. Exercise rotation through the actual stimulus scanner and incident collector.

### High: cursor progress checks still permit unbounded financial-state scans

`collectPagedScan` explicitly continues advancing scans without an item or page limit at `packages/utils/src/utils.ts:60-98`. It rejects only a cursor equal to the immediately supplied cursor, so a longer cycle such as `a -> b -> a` also runs forever. All SDK L1 pool, account, withdrawal, and order scans collect full results before deriving financial state.

Add one aggregate page/item budget at the page-collector owner, track every seen cursor, and fail closed with a typed error rather than returning partial state. Propagate the owning budget through financial callers. Current tests intentionally require unlimited advancing scans and cover only missing or immediately repeated cursors.

### Medium: a wrong node hash clears the authoritative local pending identity

The sender now records the local signed hash before RPC and rejects a different node hash before cache mutation. However, `apps/interface/src/action/actionTransaction.ts:107-123` classifies that mismatch as rebuild-ready, clears the persisted local hash, and releases the preview. The regression at `apps/interface/test/action/actionTransaction.ts:239-256` requires the deletion.

The node may have accepted the locally signed transaction before returning an inconsistent response, so acceptance is unresolved and another submission can conflict with it. Keep the local hash pending and frozen until terminal reconciliation; retain the returned hash only as diagnostic evidence.

### Medium: readiness proves neither the requested network nor the complete chain identity

`scripts/ickb-bot-systemd-update.sh:399-413` accepts either network and any nonempty object whose values are all true. It does not compare `event.chain` with the service being updated or require the actual `genesisHash` and `addressPrefix` keys produced by `packages/node-utils/src/chain.ts`. A valid event from the wrong network or an incomplete all-true object can therefore authorize rollout.

Pass the expected network into the probe and require exact network, genesis-hash, and address-prefix matches. Current fixtures use synthetic `chain` and `genesis` keys, so their green result does not prove the production schema. The trailing-separator failure currently masks most wrong-network acceptance because readiness fails earlier; this schema check becomes load-bearing as soon as path identity is corrected.
