## High Findings

### 1. Network acceptance can be reported as a hashless send failure

The installed CCC 1.17.0 `Client.sendTransaction` obtains the transaction hash from `sendTransactionNoCache`, then awaits local `cache.markTransactions` before returning it. A post-acceptance cache failure therefore rejects the same promise after the transaction is already identifiable. Stack consumers bind identity only after that full promise resolves: `packages/bot/src/bot/loop.ts:239-259` emits `send_failed` without a hash, `apps/interface/src/action/actionTransaction.ts:90-113` releases the transaction as pre-broadcast, and `packages/validation/src/tester/runtime/testerAttempt.ts:144-151` never records it. Sign first, derive the final transaction hash locally, adopt it at the network-acceptance boundary, and classify all later failures as hash-preserving post-broadcast failures. Test acceptance followed by cache/bookkeeping failure in each consumer.

### 2. Production update mutates the only live checkout without rollback or readiness

`scripts/ickb-bot-systemd-update.sh:291-303` stops the sole service, pulls and installs in place, checks, starts, and asks systemd for immediate status. A failed pull/install/check leaves production stopped; updaters are not serialized; there is no previous release to restore; and service process start does not prove bot preflight readiness. Prepare an immutable sibling release under a lock, verify it before switching, wait for bounded application readiness, and restore the prior release on failure.

### 3. Interface pending ownership still disappears on document reload

`apps/interface/src/query/pendingTransactionQuery.ts:35-55` stores pending identity only in one in-memory `QueryClient`; `:58-97` also stores the hash only after the submission promise resolves. A reload or crash after a normally returned broadcast forgets the financial intent, while an acceptance-before-promise-failure is also exposed by finding 1. Persist a versioned chain/account/hash record at network acceptance, validate and hydrate it on startup, and test a fresh `QueryClient` plus interruption at the acceptance boundary.

## Medium Findings

### 4. Confirmation still has a status-to-tip reorg race

`packages/sdk/src/send/wait_transaction.ts:118-153` refreshes committed inclusion, then `:174-186` separately reads the tip and returns the earlier response when depth is sufficient. A reorg between those reads can orphan the transaction immediately before success. Revalidate the transaction's committed block identity after the tip/depth read, or query one coherent inclusion proof, and test a reorg specifically between status and tip calls. This is narrower than cycle 7's stale-response finding, which was otherwise fixed.

### 5. Public chain scans have no aggregate work bound

`packages/utils/src/utils.ts:18-39` explicitly materializes every yielded result and treats page size only as an RPC page size. Public DAO, Core, Order, and SDK scans then collect complete pools and may issue per-cell origin or ownership lookups. Large pools can cause unbounded RPC work, memory use, and stale decisions. Add explicit aggregate cell/group/lookup budgets and return truncation or resumable cursor evidence rather than silently presenting partial data as complete.

### 6. L1 planning state combines uncoordinated query moments

`packages/sdk/src/client/sdk_l1_class.ts:106-122` reads account cells after system state; `:128-157` samples one tip and then performs independent pool, order, fee, balance, and withdrawal scans without a final fence. The SDK documents this as best-effort, but bot and interface callers use the composite for one policy decision and transaction build. Reorg or indexer skew can combine cells that never coexisted, producing failed sends or incorrect transient policy. Preserve the best-effort contract explicitly, add bounded whole-read retry on detected tip replacement, and test skewed multi-scan inputs. Chain validation remains the hard spend backstop.

### 7. Interface confirmation has no aggregate deadline

`apps/interface/src/action/actionTransaction.ts:173-193` catches each finite wait-window timeout inside `for (;;)`. A pending, dropped, or unreachable transaction keeps the interface in confirmation forever unless manually cancelled. Apply one aggregate attempt deadline that retains the hash and exposes confirmation-only retry without rebroadcast.

### 8. Active production logs and launch history remain unbounded

`scripts/bot/launcher/runtime/execute.ts:36-45` copies output for the child lifetime, and `scripts/bot/launcher/logs.ts:43-47` appends without a byte bound. Quota enforcement runs before launch and excludes the active slot; `logs.ts:95-119` reads the complete append-only launch history to select a slot. Rotate active output by bytes and bound or compact launch history.

## Low Finding

### 9. Relative order pointers can resolve before output zero

Signed negative relative distances are valid protocol data, but `packages/order/src/model/order_data.ts:122-127` adds the distance without rejecting a negative result. At output zero, distance `-1` yields an invalid negative-index outpoint; production grouping currently fails closed because no master matches it. Mirror the underflow guard in `packages/core/src/cells.ts:226-233`, retain valid backward references, and test both underflow rejection and a resolvable negative distance.
